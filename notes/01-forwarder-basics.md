## 클로센세이 피드백
Q1. Bindplane은 구글 꺼? 다이나트레이스 꺼?
둘 다 아닙니다. 독립 회사예요. 원래 이름은 observIQ로, OpenTelemetry 프로젝트의 상위 10위 기여자이자 텔레메트리 파이프라인 분야 업체였는데, 2025년 1월 자사 대표 제품명을 따라 Bindplane으로 사명을 변경했습니다. 구글과는 2018년부터 파트너였고, 2025년에 파트너십을 확장해 OpenTelemetry 기반 관측/보안 솔루션을 함께 제공하기로 했습니다. 인수가 아니라 공식 파트너 + 번들 제공 관계예요 — 구글 클라우드 Observability 및 SecOps 고객 전원에게 Bindplane의 한 에디션이 추가 비용 없이 제공됩니다. PRWeb + 2
Dynatrace는 완전히 별개의 관측가능성(observability) 회사고, 구글이 꿀꺽한 적 없습니다 (독립 상장사). 아마 OTel 생태계 글을 읽다가 여러 벤더 이름이 섞이면서 생긴 혼선 같네요. 입사 전에 바로잡아서 다행 — 회의에서 "다이나트레이스 기반이죠?"라고 했으면 아찔했겠죠. 이래서 의문점을 적어두고 확인하는 겁니다.
Q2. BYOP가 뭔 말이여
Bring Your Own Project = "네 GCP 프로젝트 가져와". 구조를 보면 이해됩니다:
[일반 상태]
SecOps(SaaS) ─ 수집 메트릭이 구글 내부 살림에 존재 → 당신은 못 봄

[BYOP 활성화]
SecOps ──연결──> 당신 회사의 GCP 프로젝트
                  └─ 수집 메트릭이 "당신의" Cloud Monitoring에 도착
                     └─ 그제서야 알림 정책 생성 가능
SecOps는 구글이 운영하는 SaaS라서, 기본적으로는 "당신 로그가 얼마나 들어오고 있는지"에 대한 메트릭이 구글 쪽 살림에 머뭅니다. BYOP는 당신 SecOps 테넌트를 당신 회사 소유의 GCP 프로젝트에 묶어서 그 메트릭을 당신 쪽으로 흘려보내는 기능이에요. 이게 꺼져 있으면 메트릭이 안 보이고 → Cloud Monitoring 알림을 만들 수 없고 → 침묵 탐지 불가. 그래서 입사 후 첫 진단 질문에 "BYOP 켜져 있나요?"가 들어가는 겁니다. 노트에 적은 "브링유어 온 피자냐" — 절반은 맞았네요, 피자 대신 프로젝트.
Q3. Cloud Monitoring vs Silent Host Monitoring
이 둘은 경쟁 관계가 아니라 층위가 다릅니다:

Cloud Monitoring = 플랫폼. GCP의 범용 감시/알림 서비스 (화재경보 시스템 그 자체)
Silent Host Monitoring(SHM) = 그 플랫폼 위에 차리는 레시피/활용법 (화재경보를 "주방에, 이 민감도로" 설치하는 설정법)

## 침묵 탐지 두 층위: 컬렉터 단위 vs SHM

| 구분 | 컬렉터 단위 감시 | SHM (호스트/소스 단위) |
|---|---|---|
| 잡는 것 | 포워더 3호기가 통째로 침묵 | 포워더는 살아있는데 뒤의 서버 X가 로그 끊음 |
| 방법 | 컬렉터별 ingested log count 임계값 | 호스트명을 ingestion label로 실어서 소스별 메트릭 생성 |
| 추가 작업 | 거의 없음 | 파이프라인에 라벨 설정 필요 |

- 둘 다 동력원은 같은 Cloud Monitoring 메트릭
- 포워더 생존 != 모든 소스 생존. 그래서 두 층위 다 필요
